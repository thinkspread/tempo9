Generated by running the models, not by reading the code. The generator

A support claim is worth what its evidence is worth, and reading the code is
not evidence that a file loads and answers. So this table has to be produced
by serving requests: `_SUPPORTED_ARCHS` names seven
architectures and the C++ registry names thirty, and neither number is the
number that answers a prompt.

## Two axes, not one: architecture and tokenizer

GGUF direct load accepts seven architectures: `qwen35`, `qwen35moe`, `gemma4`,
`qwen2vl`, `qwen3`, `qwen3moe`, and `llama`. The last one covers the Llama line
and most of Mistral.

But the architecture field does not tell you whether a file will run, because
the tokenizer is a second axis and it is invisible from there. Mistral 7B v0.3
maps all 227 weights and builds its graph — the architecture work was done for
it — and its `tokenizer.ggml.model` is SentencePiece while Llama 3.x writes
`gpt2`. Both are `architecture=llama`.

SentencePiece now runs inside the engine, so both sides of that split work:

| family | arch | tokenizer | tokenized by |
|---|---|---|---|
| Llama 3.1 / 3.2 / 3.3 | llama | gpt2 | Swift (GGUFKit) |
| Mistral v0.1 – v0.3 | llama | SPM | engine |
| Llama 2, CodeLlama, Vicuna | llama | SPM | engine |
| Qwen3.5 / Qwen3 / Gemma 4 | own | gpt2 / gemma4 | Swift (GGUFKit) |

Two implementations in two languages, and the split is deliberate rather than
historical. Byte-level BPE needs a unicode regex pre-tokenizer, which is the
expensive half to port and the half with no correctness pressure to move.
SentencePiece needs none, and it is the only tokenizer a GGUF gets on a
platform where there is no HuggingFace repo beside the file — the Python path
requires one. The engine refuses a dialect it does not implement by name; it
never guesses, because a vocabulary read with the wrong algorithm still
produces ids, and those ids decode to fluent text from the wrong distribution.

The SPM ids are checked per-token against `llama-tokenize` rather than by
running the model: `tests/cpp/tokenizer/run_spm_parity.sh`, 18 cases across two
vocabularies.

## Why there is a LONG10K column

Every check in this table used to be a short prompt, and the table was green
for two models that produced word salad on anything past ~8k.

`llama_v2` built its RoPE with no `rotary_base`, so the C++ default of 10000
applied — Llama 1/2's value, the only one that graph had ever seen. Mistral
v0.3 is 1e6 and Llama 3.1 is 5e5. A wrong theta does not fail; it is correct at
short range and degrades with distance. 8021 tokens answered "Paris", 9021 came
back half-wrong, 10021 was word salad, and every test written before that one
was under 8k.

It looked like a tokenizer bug, because it appeared the day SentencePiece
landed. The experiment that separated them was Llama 3.1 8B, which uses the
Swift byte-level BPE path and degrades identically at 10k, against Qwen3.5-4B,
which is fine at 10,026 tokens. Same graph, different tokenizers — so the
graph. Length is its own axis and now it has a column.

`N/A` in that column is not `FAIL`: TinyLlama declares a 2048-token context, so
a 10k prompt is something it never claimed to do. Scoring it FAIL would be the
same error as scoring a missing file FAIL, so the harness reads
`context_length` from the file and says so.

## Does an agent actually run on this?

OpenClaw drives Mistral 7B v0.3 through the engine: its 10,690-token system
prompt renders, the model answers on topic, and the run ends `stopReason=stop`.
Two things had to be fixed to get there and both were outside the tokenizer --
the RoPE theta above, and the chat template.

Mistral v0.3 and the Llama-2 line reject a system role outright ("Conversation
roles must alternate"), and every agent front end sends one, so those models
were reachable by `curl` and not by an agent. The system text now folds into the
first user turn on render failure, which is the accommodation llama.cpp and
Ollama make. Only on failure: a template that accepts a system role never takes
that path, so no prompt changes for the models that already worked.

What it does *not* do is drive tools well. Mistral 7B v0.3 is not a strong
agentic model and OpenClaw's harness expects tool-calling it does not reliably
produce. That is a model property, not a pipeline one, and the distinction is
worth keeping: the pipeline is proven, the model is what it is.

## Six harness bugs this table caught, all of the same kind

The harness itself lives with the engine's test tooling and is not in this
repository; these are kept for the failure shape, which is not specific to
it. Each reported a state the machine was not in, and each was found only
because a row disagreed with something already observed by hand.

**The LOAD column could not fail.** `ask()` takes the expected substring as
`$want`, and the LOAD check passed `""`. `grep -qiF ""` matches every input,
including *no* input — so LOAD read `ok` for a model that had just refused to
load in front of me. Every `ok` in the previous table was vacuous. An empty
`$want` now means "answered at all", checked against the stripped answer body,
with the known-good model kept as a positive control so the fix is confirmed in
both directions.

**`FAIL` with no reason** sends the reader back to the machine, which is the
same dead end as omitting the row. A failing load now keeps whatever the engine
said — which is how the tokenizer axis got a name instead of a shrug.

**The LONG10K column reported FAIL for everything, including a model I had just
watched answer at 10k by hand.** `ask()` already appended `--max-length 8192`,
so the column's own `--max-length 32768` arrived as a second, ignored flag and
every long prompt overran an 8k window. The length is a variable now. Same
shape as the others: a check reporting a state the machine was not in.

**Two naming worlds, both real.** `stat()` cannot tell a missing file from a
wrong name. Projectors drop the whole tuning and quant suffix
(`gemma4-12b-it-q4ks` → `gemma4-12b-mmproj-f16`); Core ML towers use the
HuggingFace name (`qwen35-9b-imat-q4ks` → `Qwen3.5-9B`). The second is built
with `awk`, not `sed`'s `\U` — a GNU extension that BSD sed renders as a
literal `U`, so the lookup asked for `Qwen3.5-9BU` and reported ABSENT for a
tower sitting right there.

**A waiter that waited for itself.** `until ! pgrep -qf "support_matrix.sh"`
matches the waiting shell's own command line, which contains that string, so
the loop blocks forever on a run that finished long ago. Not part of the
harness, but the same shape, and it cost real wall-clock: the table was
complete and being reported as still running.

There is no `timeout` on macOS either; the harness uses perl's `alarm`. A
previous bench that wrapped the missing binary failed every arm silently.

## What all six have in common

None was a wrong answer about a model. Every one was a tool reporting a state
the machine was not in — `ok` for a load that failed, `FAIL` for a prompt that
worked, `FAIL` for a context that was never claimed, ABSENT for a file sitting
right there, still-running for a finished run. A support matrix exists to be
trusted by people who cannot read the source, so the failure mode that matters
most here is not a model that breaks. It is a green row that means nothing.

Which is why every check in this table is paired with the experiment that makes
it fail: the LOAD fix was confirmed by watching Mistral flip to FAIL *and*
llama32-1b stay ok; the LONG10K column was confirmed by rebuilding a llama
graph without its `rotary_base` and watching TEXT stay PASS while LONG10K went
red — exactly the state the old table would have shown as fully green.
